## 4. 必须区分的现状与目标

| 项目        | 已观察到的源码事实                                           | 本方案处理                                                         |
| ----------- | ------------------------------------------------------------ | ------------------------------------------------------------------ |
| 语言选择    | 当前默认常量为英文，生产再匹配浏览器语言                     | 沿用现有机制，保留production/staging与dev/test区别，已保存偏好优先 |
| 原料“上限”  | 正量生成固定采矿配方目标，可产生盈余；不是普通物品输入上限   | 等价基准保留此建模。若将来要改为纯上限，作为另一次功能调整         |
| 传输整数    | `transfer_` 标记整数，但 intopt 开关由机器限制遍历设置       | 需要在新实现按实际整数变量集合启用 MIP，单独开启传输也必须生效     |
| 净水额度    | 只有两个普通配方变量同时存在才添加联合限制                   | 新实现必须覆盖任意子集及显式配方目标，属于预期约束完整性修正       |
| 机器归属    | 旧循环按 producers 包含某机器判断，而非实际选择机器          | 当前数据应回归；多生产者可选场景按实际机器归属统计，避免误计       |
| hidden 排序 | `indexOf` 为 -1 时 `??` 不会兜底；现有资源组件测试仅检查创建 | 不搬实现缺陷；用显式所有权和排序规则，增加边界行为验收             |
| 旧通用修复  | 目标分支包含已摘入的上游步骤层级修复                         | 新上游已用 Set 去重并补回层级，直接验证                            |

缺陷依据来自静态源码审计；具体受影响输出仍需运行验证。发布前应按 [06](06-execution-and-acceptance.md) 的差异处理规则，将正常场景等价性与已知缺陷修正分别记录。

### 项目文档范围

以01固定的ark-endfield-3rd-test源提交中的README.md、docs/flags.md、docs/mod-data.md、docs/recipe-flags.md为已有信息范围。随相应实现落地，校正产品说明、原有链接、字段名称、参数类型、标志语义和失效措辞，使其与实际最终代码一致；保留原文用途和信息范围，不为迁移扩写成开发手册。

README已有项目介绍、主页、fork来源和问题反馈链接，可以按实际情况校正；不追加构建/迁移/验收执行入口、脚本命令目录、开发进度或执行记录、数据版本及统计栏目。已有数据说明中的字段或脚本引用可以在原主题内校正，例如position变为x/y、pipe模型变化及旧标志的实际承接方式。

上游文档中超出本项目原有范围的章节不因同步而自动引入。迁移方案的基线、验收计划和技术版本契约只用于设计，不自动成为项目日常文档的新栏目或导航链接。文档随已实现内容校订，不提前声称规划功能已经可用。
