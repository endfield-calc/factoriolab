# 实施顺序与验收

本文件定义实现任务及完成条件。源码和文档静态复核不能替代运行验收；各场景只有执行并保存输入、结果及提交身份后才能标为通过。

## 1. 分阶段实施

| 阶段          | 前置条件 | 工作内容                                                                          | 完成标准                                              |

界面静态骨架可以提前做，但不能用它代替数值或兼容验收。按阶段逐步提交，每个实现阶段完成可独立检查的改动并通过对应检查后提交；较大阶段继续按职责拆分，不积累为一次最终提交。提交描述写清恢复的行为和实际执行的检查，不把未执行的验收写成已通过。

`.agents/`和`.codex/`仅保留在本地工作区，不进入迁移及后续同步提交。每次按本步骤的明确路径选择暂存，检查暂存文件清单与完整差异，确认两个目录及无关改动均未包含在内，再创建提交；相关说明只保留在本迁移方案，不追加到既有项目文档。

## 2. 样本和比较规则

采用固定的 aef v1.5.3 输入，同时运行旧来源提交与新实现。每条记录至少包含：普通目标、六项资源配额及开关、机器/传输/节点设置、地点、排除项、成本、显示单位、求解模式和完整链接。输出记录目标产出、原料采集/消耗/盈余、配方运行量、机器数量、传输选择、净水节点占用、功耗、总成本及求解状态。

| 样本组  | 来源与用途                                                                                                                                              |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| G01–G02 | 源分支UserTips前两条示例：谷地毕业、谷地理论最高调度券；从固定提交读取原URL，作为正常回归样本                                                           |
| G03     | 第三条武陵旧版示例属于修正样本：原压缩链接含已退休xiranite_powder配方；保留原URL，并以明确别名恢复4台原配方目标，不能拿旧版过滤该目标后的结果做等价标准 |
| G04     | 不启用资源面板的普通输出/机器/最大化/限制场景；确认基础上游能力仍可用                                                                                   |
| G05     | 谷地预设与武陵1.5预设分别作为基准，另保存各开关独立启用组合                                                                                             |
| G06     | v11 明文和压缩链接各一份，包含全部隐藏类型、cet、odr=3、地点与排除项                                                                                    |
| G07     | 只启用传输的整数反例；净水只保留一个配方的额度反例；显式目标绕过约束反例                                                                                |
| G08     | 旧 preferences、多个 states.aef、router、black主题及无效存储的离线样本                                                                                  |

正常场景比较物理量和目标函数；多最优解时允许具体配方组合不同，但必须满足同一约束且目标值相同，不以行顺序或图布局要求逐字一致。Rational 比较应尽量使用精确值；对 GLPK 数值结果使用明确且一致的容差，例如绝对与相对误差各1e-7，并记录用于整数判断的容差。整数约束满足、隐藏状态不丢失、实体 ID 正确属于独立硬条件，不能被宽容差掩盖。

G03属于退休配方修正场景，按05中的物理字段证据检查别名和4台目标未丢失。G07属于求解约束修正场景：先给出能区分 LP 松弛与整数解、能超出节点额度的输入，独立检查新结果满足业务约束。若旧版输出违反预期，报告为“修正旧缺陷导致差异”，不要为追求逐值一致撤销约束。MIP 总成本比较使用整数解目标值；不能与旧版误报的 LP 成本直接做相等断言。

整套最优数值由固定源码运行生成；下文微型期望来自数据与公式，仍须由实际程序验证。不得用未执行的计算结果填充基准。

## 4. 质量检查与范围控制

实现阶段使用新上游实际脚本：`npm ci`、`npm run prettier`、`npm run lint`、`npm run test:ci`、`npm run build`。对新数据转换、旧状态兼容和约束编译写有辨别力的测试；不要以 resource-input 的 should-create 测试替代数值验收。

保留上游通用测试及其测试夹具；检查测试默认 mod 不再依赖生产目录里的 spa。保留新锁文件的依赖组合，出现测试差异时调查语义，不直接跳过大批测试以获得绿灯。

## 5. 发布门槛与回退

发布前F01–F22与D01–D05必须有对应A场景证据；P0 的数据、兼容、约束和整数解成本问题不能作为“已知限制”遗留。正常场景等价、旧缺陷修正、上游新行为分别列出差异与理由；数值结果、完整输入和提交 SHA 应能复查。

准备按站点可恢复的上一份静态产物与发布记录。发布后检查缓存升级、示例链接和已有存档，再扩大使用；若状态恢复或计算失真，回退对应产物并保留用户原始存储，不通过清空所有缓存/存档掩盖问题。实际部署在实现与发布阶段执行。
