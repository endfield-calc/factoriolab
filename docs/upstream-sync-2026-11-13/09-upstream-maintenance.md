# 后续上游同步设计

## 1. 维护目标

初次迁移建立以上游main为祖先的实现分支；此后按正常上游血缘更新本地产品。功能集中在独立目录，通用代码只保留有说明的扩展接点和少量通用修复。目标是让后续同步能清楚识别“上游演进、接点适配、本地规则变化”，而不是每次重新解释数百个散落补丁。

上游文件变化并非必须为0。增加一个稳定、可测试的通用接点，优于复制整个Solver/SettingsStore、构建时覆盖源文件或在各页面反复判断aef；也不为降低表面文件数而把全部功能塞进一个巨型适配器。

## 2. 四种差异的处理

| 差异类型                             | 存放方式                                                                 | 维护规则                                                          |
| ------------------------------------ | ------------------------------------------------------------------------ | ----------------------------------------------------------------- |
| 业务规则、预设、旧编码、品牌、专属UI | `src/endfield`、`public/data/aef`、`public/endfield`、`scripts/endfield` | 集中演进，通用核心不反向导入业务实现                              |
| 接入契约及其默认实现                 | `src/extensions`和登记的调用位置                                         | 保留上游默认路径；接口改变时只改适配器与少量接点                  |
| 对通用算法的必要能力/修复            | Solver的声明约束与MIP、PerDay等小改动                                    | 独立提交，有不含aef规则的通用测试；上游提供等价能力后删除重复实现 |
| 产物选择与环境配置                   | 产品配置、本地构建入口和工作流                                           | 过滤要发布的数据和入口，不批量删除通用源码或重写上游构建系统      |

当前功能范围不变：生产产物只包含aef游戏数据；测试所需的其他数据转为隔离夹具或明确排除的测试输入。保留上游游戏类型和通用算法，不等于向用户开放其他游戏。

## 4. 避免长期漂移的实现约束

M04 的共享验证还包括 `src/app/main/data/recipe-detail/recipe-detail.spec.ts`：实际详情 DOM、调整后的成本与同一目标的求解成本共同随电力权重变化。M08 的 `PresentationExtension.nameToggleLabel` 提供名称开关文案，`stepFragment` 提供行链接片段；默认名称开关隐藏、片段为 `undefined`，产品文案键及资源面板片段只在独立适配器中定义。原 `workspaceLink` 仍专门表达保留整个工作区的序列化策略，不与片段导航混为同一职责。

1. 不复制上游大类、整页模板、旧package-lock或主题体系；不靠继承后重写大部分私有实现维持一个“同名新类”。
2. 不用postinstall补丁、正则改源码、运行时monkey patch或fileReplacements覆盖Solver/Store。构建可以生成数据、词典和站点元数据，但不能把源代码改写隐藏在构建过程里。
3. 共享代码不出现资源ID、地区额度、xiranite例外或业务URL；必要身份注册、独立规则表和兼容数据除外。显示策略通过准备后的视图模型读取，不在每个模板加aef条件。
4. 新旧URL通过StateExtension衔接；不复制RouterSync/Migration，不向全局普通目标枚举持续追加专属类型。旧hash只能解码，aef新hash只追加；不借用上游清理/复用槽位的脚本。
5. 新扩展关闭时维持上游路径，纯领域函数不回读全局Store；调用方使用自身服务准备声明，扩展不注入Normalization等反向依赖其调用者的服务。只启用aef的生产配置与覆盖通用行为的测试配置分开。
6. 维护性不以删掉上游测试、跳过质量检查或扩大容差换取。需要迁移夹具时保留其验证能力，并登记其生产排除方式。

## 5. 提交与比较方式

实现提交按职责拆分：中立接点、数据/兼容、终末地状态与计算、UI/品牌、构建交付。按06的阶段逐步提交，较大阶段拆成多个可独立检查的提交，通过对应检查后提交，不在迁移全部结束后集中提交。每次小型通用修复与业务规则变更分开提交，使评审能直接比较上游默认行为和本地扩展。

迁移及后续同步提交均排除`.agents/`和`.codex/`。两目录保留在本地工作区；每次只暂存当前步骤的相关路径，提交前核对暂存文件清单与差异，避免将本地代理配置和无关改动带入提交。

首次迁移从上游main固定SHA开始；`ark-endfield-3rd-test`只提供行为和素材证据，不能作为需要重放的提交队列。完成后保留该上游祖先；后续同步可以将更新的upstream/main合入迁移后的交付分支。不要再次从旧fork重建，也不要反复摘取本地历史来制造一条看似干净但无法跟踪上游的分支。

审核时同时看完整最终差异和接点组。数据体积大、独立目录增加多，不代表核心改动多；核心只改几行但通过私有API耦合多个Store，同样不满足维护目标。
