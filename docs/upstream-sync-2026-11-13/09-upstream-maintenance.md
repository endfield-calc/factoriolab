# 后续上游同步设计

## 1. 维护目标

初次迁移建立以上游main为祖先的实现分支；此后按正常上游血缘更新本地产品。功能集中在独立目录，通用代码只保留有说明的扩展接点和少量通用修复。目标是让后续同步能清楚识别“上游演进、接点适配、本地规则变化”，而不是每次重新解释数百个散落补丁。

上游文件变化并非必须为0。增加一个稳定、可测试的通用接点，优于复制整个Solver/SettingsStore、构建时覆盖源文件或在各页面反复判断aef；也不为降低表面文件数而把全部功能塞进一个巨型适配器。

## 2. 四种差异的处理

| 差异类型                             | 存放方式                                                                 | 维护规则                                                          |
| ------------------------------------ | ------------------------------------------------------------------------ | ----------------------------------------------------------------- |
| 业务规则、预设、旧编码、品牌、专属UI | `src/endfield`、`public/data/aef`、`public/endfield`、`scripts/endfield` | 集中演进，通用核心不反向导入业务实现                              |
| 接入契约及其默认实现                 | `src/extensions`和登记的调用位置                                         | 保留上游默认路径；接口改变时只改适配器与少量接点                  |
| 对通用算法的必要能力/修复            | Solver的声明约束与MIP、PerDay等小改动                                    | 独立提交，有不含aef规则的通用测试；上游提供等价能力后删除重复实现 |
| 产物选择与环境配置                   | 产品配置、本地构建入口和工作流                                           | 过滤要发布的数据和入口，不批量删除通用源码或重写上游构建系统      |

当前功能范围不变：生产产物只包含aef游戏数据；测试所需的其他数据转为隔离夹具或明确排除的测试输入。保留上游游戏类型和通用算法，不等于向用户开放其他游戏。

## 3. 接点清单与审计信息

实现时在本文件各行补齐实际文件、导出符号与契约测试名称，以最终内容直接替换。不得仅写“扩展一下”后留下未登记的共享文件改动。

| 编号 | 接点组             | 允许的变化                                                  | 同步时检查                                                            |
| ---- | ------------------ | ----------------------------------------------------------- | --------------------------------------------------------------------- |
| M01  | 组合入口与产品注册 | 绑定四类扩展，登记游戏身份；运行目录由配置筛选              | 注入生命周期、路由装配、目录类型是否变化                              |
| M02  | 默认值与语言       | EffectiveDefaults贯通初始化、补缺、差分编码、modified和重置 | production/staging、偏好覆盖、刻意设回上游默认的往返与全部重置        |
| M03  | 数据与翻译         | 使用上游schema/资源管理，加入数据适配和词典合成             | schema、httpResource加载/错误状态、英文游戏翻译                       |
| M04  | 配方成本出口       | 只覆盖成本，其他准备仍由上游完成                            | raw/adjusted区别、配方目标系数、详情与求解的数据一致性                |
| M05  | 完整计算上下文     | 纯扩展声明，由调用方准备；提供完整设置、owner及勾选读取     | 归一化时机、间接DI环、设置/勾选owner、合计与标题范围                  |
| M06  | 模型构造和MIP      | 绑定两类变量、应用中立约束与整数标记，统一读解              | 变量创建顺序、全部变量种类、求解状态和目标值API                       |
| M07  | 状态编解码与恢复   | 委托旧协议适配；收集扩展状态变更；读写ef段                  | 压缩/明文、短ID、有效默认值、派生设置/勾选、导航/存档/stepHref与ready |
| M08  | 展示与产品元数据   | 插槽、集中显示及步骤动作/链接owner、品牌与导出              | 步骤编辑/重置/清空勾选不写错Store、派生链接不双计、新组件与无障碍     |
| M09  | 通用小改动         | PerDay及确有必要的中立能力                                  | 上游是否已实现，能否移除本地重复改动                                  |
| M10  | 构建、资产与发布   | 选择生产数据、合成词典/元数据、生成最终SW                   | 输出路径、静态资产规则、质量命令、发布目的地                          |

每个共享文件差异必须能归入一个接点，并能说明默认行为、输入输出、验证方式及上游变化时的替换边界。实际接点文件超出03预期时先重新审视设计，不能默认为可无限扩散。

中立契约位于 `src/extensions`：`PRODUCT_PROFILE` / `EFFECTIVE_DEFAULTS`、`CALCULATION_EXTENSION`、`STATE_EXTENSION`、`PRESENTATION_EXTENSION` 分别提供上述四类接点的上游默认实现。`immutableValue` / `mutableValue` 约束只读快照与 Store 写入边界；`WorkspaceLifecycle` 提供不依赖 RouterSync 或计算 Store 的恢复票据与就绪状态。未装配产品提供者时不添加派生目标、约束、状态参数或页面插槽，保留上游默认值和成本。契约测试为 `src/extensions/extensions.spec.ts` 中的 `Neutral extension defaults` 和 `Workspace recovery lifecycle`；这些测试只验证契约与生命周期，不替代调用位置及双配置的运行验收。

## 4. 避免长期漂移的实现约束

1. 不复制上游大类、整页模板、旧package-lock或主题体系；不靠继承后重写大部分私有实现维持一个“同名新类”。
2. 不用postinstall补丁、正则改源码、运行时monkey patch或fileReplacements覆盖Solver/Store。构建可以生成数据、词典和站点元数据，但不能把源代码改写隐藏在构建过程里。
3. 共享代码不出现资源ID、地区额度、xiranite例外或业务URL；必要身份注册、独立规则表和兼容数据除外。显示策略通过准备后的视图模型读取，不在每个模板加aef条件。
4. 新旧URL通过StateExtension衔接；不复制RouterSync/Migration，不向全局普通目标枚举持续追加专属类型。旧hash只能解码，aef新hash只追加；不借用上游清理/复用槽位的脚本。
5. 新扩展关闭时维持上游路径，纯领域函数不回读全局Store；调用方使用自身服务准备声明，扩展不注入Normalization等反向依赖其调用者的服务。只启用aef的生产配置与覆盖通用行为的测试配置分开。
6. 维护性不以删掉上游测试、跳过质量检查或扩大容差换取。需要迁移夹具时保留其验证能力，并登记其生产排除方式。

## 5. 提交与比较方式

实现提交按职责拆分：中立接点、数据/兼容、终末地状态与计算、UI/品牌、构建交付。按06的阶段逐步提交，较大阶段拆成多个可独立检查的提交，通过对应检查后提交，不在迁移全部结束后集中提交。每次小型通用修复与业务规则变更分开提交，使评审能直接比较上游默认行为和本地扩展。

迁移及后续同步提交均排除`.agents/`和`.codex/`。两目录保留在本地工作区；每次只暂存当前步骤的相关路径，提交前核对暂存文件清单与差异，避免将本地代理配置和无关改动带入提交。

首次迁移从上游main固定SHA开始；`ark-endfield-3rd-test`只提供行为和素材证据，不能作为需要重放的提交队列。完成后保留该上游祖先；后续同步可以将更新的upstream/main合入迁移后的交付分支。不要再次从旧fork重建，也不要反复摘取本地历史来制造一条看似干净但无法跟踪上游的分支。

审核时同时看完整最终差异和接点组。数据体积大、独立目录增加多，不代表核心改动多；核心只改几行但通过私有API耦合多个Store，同样不满足维护目标。

## 6. 后续同步流程

| 步骤         | 操作与产出                                                                           |
| ------------ | ------------------------------------------------------------------------------------ |
| 固定输入     | 确定交付分支HEAD、原上游基线、新upstream/main；保存可回退的源码与静态产物            |
| 获取上游变化 | 在隔离同步分支合入新上游，读取其实际diff与依赖/schema变化；保留上游提交血缘          |
| 分类处理     | 按M01–M10定位冲突与语义变化；先更新契约/适配器，再检查独立业务模块是否真的需要变化   |
| 减少本地差异 | 上游已有等价机制时复用并删除本地重复逻辑，保留协议表、别名与业务规则自身             |
| 双路径验证   | 运行上游默认配置的通用测试，及aef配置的功能、兼容、成本/约束和构建验收               |
| 检查最终差异 | 无未登记的共享改动、无源覆盖脚本、无散落业务条件；新依赖和数据规则都在最终方案中说明 |
| 交付与回退   | 形成固定基线、测试结果及最终产物；按双站流程发布，可回退对应产物并保留用户状态       |

项目文档随相应实现检查，仅在原有用途和信息范围内校正描述及链接；不把同步过程、执行入口或数据版本清单写入README等原文没有这些内容的文档。D05/A31作为同步交付检查，与代码语义核对一起完成。

文本冲突解决不代表同步成功。即使Git可自动合并，仍需检查成本时机、变量归属、默认值、URL/hashing、资源加载和SW等语义边界。

## 7. 完成条件

维护设计对应06中的A27–A30：共享差异可追溯到接点；停用扩展时通用路径成立；状态/计算快照一致；旧链接与额外状态完整往返；完成一次可复查的上游更新演练；A31检查既有项目文档与实现一致且没有扩写新主题。

若没有新的上游提交可用，演练使用隔离分支中的受控上游侧变化，覆盖一个UI接点和一个状态/计算接点，验证合并后通过相同契约测试；不得把这种演练写成已兼容未来所有上游版本。

方案文档始终维护最终契约和当前接点。Git中的实际fork/祖先证据、旧协议定义和部署release元数据属于必要技术事实，继续保留。
