# EndfieldLab 上游同步迁移方案

本方案定义从上游 main 新建实现分支、重建 `ark-endfield-3rd-test` 有效功能的范围、设计与验收。应用实现按06的阶段和验收执行，本地交付与实际部署分别核验。

“当前分支”固定指 `ark-endfield-3rd-test`，其他本项目分支不作为需求或实现来源。各文档只描述最终要求、来源证据和当前复核结论。

## 目标与设计原则

1. 首次迁移从实施时的上游 main 创建分支，不把旧分支整体 merge、rebase 或 cherry-pick 进来。完成后保留这条上游血缘，后续可以正常合入上游 main。
2. 运行时只提供《明日方舟：终末地》与 aef 数据。其他游戏的产品入口和数据不发布；上游通用实现、类型及隔离测试夹具保留，减少无关删除和未来冲突。
3. 以功能、状态含义和计算契约作为等价标准，重写现有杂乱实现。业务规则集中管理，界面使用上游组件和样式，状态恢复、求解和持久化有明确职责；不要求复刻旧组件、隐藏目标编码或定时器。
4. 语言选择沿用现行机制：初始 en；production=true 时读取 `navigator.language`，转小写后先匹配完整代码、再匹配语言前缀，不支持则英文；已保存偏好覆盖初始值，手动选择持久化。staging同样匹配浏览器，dev/test不匹配。
5. 终末地规则、品牌、数据适配和旧协议集中在独立模块，通过有限、登记的上游接点接入。通用核心只依赖中立契约及默认行为，不能散布 aef 条件、复制上游大类或依赖构建脚本改写源代码。
6. 已证实的缺陷允许修复，须说明业务依据、预期差异和反例验收。正常功能保持等价，错误的 LP 成本、漏约束或失效目标不作为必须复制的结果。
7. 后续上游同步的差异审计、默认路径验证、兼容回归和回退方式属于迁移完成条件，而不是实现结束后再考虑的维护事项。
8. 项目既有文档随相应实现同步校订，以当前分支已有用途和信息范围为边界，反映实际功能、字段和链接；不增加原文没有的开发记录、执行入口、数据版本等主题或栏目，也不把未实现方案写成现状。
9. 迁移按阶段逐步提交；较大的阶段继续按职责拆分，通过对应检查后提交，不积累为一次最终提交。`.agents/`和`.codex/`仅保留在本地工作区，不进入迁移及后续同步提交；每次提交前核对暂存路径与差异。

## 核查与验收边界

源码审计覆盖完整Git历史、原始差异、目标分支数据及固定上游快照。344个差异文件中有大量其他游戏数据删除，文件数不代表独立功能或开发量。

优先建立schema与hash转换、不可变计算快照、资源状态与旧协议边界。现有hash缺项及退休槽位、第三条示例的退休配方别名、MIP成本和约束完整性均有明确契约与验收。

文档静态复核不等于应用运行验收。计算、浏览器、构建发布和旧缓存升级必须在实现阶段按06执行；不得将未执行的场景写成已通过。
